THE PROBLEM

DIG pre-finances land and house purchases across the US — buyers hold the title and repay on clear monthly schedules instead of a 30-year mortgage. Behind that promise sit long payment plans, deposits, instalments and manual reconciliation: six-figure balances tracked across spreadsheets, where a single error is expensive and trust is fragile.

WHAT I DID

01
RESEARCH

Mapped the money, not just the screens

Modelled the full lifecycle of a financed parcel — deposit, instalment schedule, arrears, reconciliation — with the finance team before drawing a single frame. The domain, not the UI, set the structure.

02
DECISIONS

A reconciliation workbench, not a table

Chose a workbench pattern (built on shadcn/ui primitives) so an operator can match payments against schedules side-by-side, with running balances always visible. Kept the data model as the interface's backbone.

03
DESIGN

Dense data made calm

Designed a strict token system — spacing, tabular numerals, hairline dividers — so screens dense with figures stay legible. Status is carried by type and rule weight, not colour alone (accessibility + print parity).

04
SHIP

Designed to the component, then shipped it

Handed off as production React components rather than static frames, so the finance module went live without a design-to-code gap.

WHAT I'D DO DIFFERENTLY

I front-loaded the finance model and under-invested early in the empty and error states — the first operators hit edge cases (over-payment, refunds) I hadn't designed for. Next time I'd storyboard the unhappy paths in the same breath as the happy one.
